# 0005 评测链路与在线链路物理隔离

- 状态：已采纳
- 日期：2026-10

## 背景

要衡量回答质量，就得跑 LLM-as-Judge（DeepEval）。Judge 调用本身很慢（秒级到十几秒）且贵，还可能被供应商限流。

如果把 Judge 塞进客户请求链路，等于让客户为内部质量度量买单：延迟不可控、成本不可控、限流时连正常回复都受影响。

## 决策

- 客户请求**只采集脱敏 Trace** 写入 `evaluation_trace`，请求返回前绝不调用 Judge。
- 评测由独立进程 `rag.evaluation_worker` 消费，与在线 `agent_execution_worker` 完全分离。
- 采样分级：高风险、转人工、工具失败、低置信度、无知识库命中、引用异常 **100% 采样**；普通成功会话稳定 **10%** 采样。
- 成本闸门：每日 Judge 预算 `EVAL_DAILY_BUDGET=200`，单批 10 条、串行执行以降低限流风险；黄金集样本并发 `RAG_GOLDEN_EVAL_CONCURRENCY=3`。
- Trace 落库前脱敏，订单号、手机号、邮箱不进入评测库。
- 评测结果写入 `evaluation_result`，黄金集任务写入 `evaluation_job`，通过 `/api/staff/evaluation/*`、`/api/staff/rag/evaluation*` 暴露。

## 后果

正面：

- 客户延迟与评测延迟完全解耦，Judge 再慢也不影响在线；
- 预算与并发有硬闸门，成本可预期；
- 失败样本可回放，评测结论可追溯到具体问题。

代价：

- 评测是**滞后的**：线上出问题的会话要等 Worker 跑完才能看到质量结论，不能实时拦截。
- 高风险会话 100% 采样会放大 Judge 调用量，预算吃紧时只能靠 `EVAL_DAILY_BUDGET` 截断，可能丢掉部分样本。
- 脱敏在采集侧完成，脱敏规则一旦漏项就是隐私事故，必须持续用测试守住。
- 新增了 `evaluation_trace`/`evaluation_result`/`evaluation_job` 三张表与一个必须独立部署的 Worker，运维面变大。
