# 0006 文档收敛为 5 份权威文档加归档目录

- 状态：已采纳
- 日期：2026-10

## 背景

仓库内外的 `.md` 一度膨胀到 43（项目内 22 + 交付批次 8 + 工作区根目录 13），同一个主题存在 3~5 个互相打架的版本：

- 接口文档有 3 份，其中 2 份还写着已经拆掉的 `app.py` 行号；
- 工单状态机有 2 份，其中一份引用了根本不存在的 `GET /api/staff/members`、`StaffMemberController`、`/dispatcher` 页面；
- 启动方式有 4 种写法（`start-all.bat`、`start-local.sh`、手动三条命令、`docs/项目现状盘点.md` 里的又一套），端口与顺序互不一致。

结果是：**新人和 agent 都读不到真相**，而且没人知道哪份是最新的。冗余文档的维护成本已经超过了它的价值。

## 决策

只保留 5 个文档位置，各司其职，主题不重叠：

| 文档 | 唯一职责 |
| --- | --- |
| `README.md` | 5 分钟跑起来：依赖、启动顺序、端口、验证方法。不讲设计 |
| `docs/ARCHITECTURE.md` | 分层与边界、模块职责、一条客户消息的旅程、依赖方向、状态机、评测、已知限制 |
| `docs/API.md` | Agent API + Java Business API 完整契约，**以 `docs/_baseline/baseline-openapi.json` 为准** |
| `docs/RUNBOOK.md` | 启动停止、排障、监控指标、压测、数据迁移、常见故障 |
| `docs/ADR/` | 架构决策记录，`NNNN-标题.md`，含背景/决策/后果 |

处置规则：

- 项目内冗余 md：事实合并进上述文档后**删除原文件**；`docs/rag-eval/` 的一次性评测报告删除，只保留结论摘要（写入 ARCHITECTURE 第 6 节）；`docs/大模型微调学习报告.md` 属学习笔记，移入归档而非删除。
- 工作区根目录的历史产物（PRD、调研、交付批次、图解 html、验证证据截图）：**只归档不删除**，统一移入 `archive/产品与研究产物/`，并写 `archive/README.md` 声明其非权威。
- `AGENTS.md` 作为给未来 agent 的活文档同步更新（目录结构、启动命令、提交前必跑项，`compileall` 目标从 `app.py` 改为 `app` 包）。

## 后果

正面：

- 同一件事只有一个说法，冲突消失；
- 新人路径明确：README 跑起来 → ARCHITECTURE 理解 → API/RUNBOOK 干活；
- agent 有稳定的读取目标，不再从过期文档里学出错误结论；
- 归档保留了历史证据，需要时仍可追溯。

代价：

- 删文件是不可逆的（依赖 git 历史兜底），所以合并必须**逐条确认独有信息已落地**，不能整段拼贴；
- 5 份文档的更新责任更重：接口改动必须同时改代码、`API.md` 和基线 spec，否则单点失真影响所有人；
- 归档目录会持续变脏，需要约定"新产出进 archive，权威结论进 docs"；
- `docs/observability/`（Grafana 看板与告警规则）作为**配置资产**保留在原位，不参与本次收敛——它不是叙述性文档。
