# 0002 以 Java 业务服务作为唯一业务真相源

- 状态：已采纳
- 日期：2026-10

## 背景

项目需要"AI 客服能真正办事"，而办事就要写业务数据（工单、派单、状态、催办）。有两条路：

1. Python Agent 直接连业务库读写，省一次 RPC；
2. Python 只做编排，所有业务读写都调 Java 接口。

直接连库在 Demo 阶段更快，但会立刻带来权限校验重复实现、状态机分叉、审计缺失、双写不一致四类问题，且 Agent 侧一旦被注入就无法限制其写权限。

## 决策

`business-service` 是核心业务系统与**唯一真相源**。Python Agent 不直接写订单、物流、工单业务表；所有业务动作必须经 `tools/`（`order_tools`、`ticket_tools`、`kb_tools`）或 `deps.business_client` 调用 Java。

配套约束：

- 客户身份以 Java Token 为准。前端传的 `customer_id`、姓名、订单号不可信，服务端用 Token 解析结果覆盖，并在 Java 侧再校验归属。
- 统一 resilience 封装（`services/resilient_client.py`）：超时、重试、熔断、并发舱壁、安全降级，禁止在路由里散落裸 `requests/httpx`。
- 写操作必须幂等：工单创建带幂等键，Java 侧 `support_ticket.request_id` 与 `(customer_id, idempotency_key)` 有唯一约束。
- Python 与 Java 之间用 `externalSessionNo` 强关联工单与会话。

## 后果

正面：

- 权限、状态机、审计只有一份实现，Python 侧无法绕过；
- Agent 被提示词注入时，最坏后果是"调了允许的工具"，而不是"改了数据库"；
- Java 可以独立演进数据模型，Python 只依赖 REST 契约。

代价：

- 一次客户提问会串行触发多次 RPC（鉴权 → 查单 → 建单），延迟与失败面变大，必须靠 `resilient_client` 的超时预算与降级兜底。
- **两个 SQLite 文件之间没有跨库事务**：Java 建单成功而 Python 落消息失败时状态不一致，只能靠接口错误码、`externalSessionNo` 和日志对账。这是已知限制，不是可以忽略的细节。
- Java 不可用时 Agent 只能安全降级，不能"先把单记在本地回头补"。

## 备选方案与放弃原因

- 直连数据库：写权限失控、状态机分叉、审计缺失，放弃。
- 本地消息表 + 最终一致：复杂度对当前阶段过高，且没有可靠的对账补偿任务，放弃（未来若引入事件总线可重新评估）。
